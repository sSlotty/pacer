# Backlog: รองรับผู้ใช้หลายคน

> **สถานะ:** ข้อเสนอ ยังไม่เริ่มทำ · **บันทึกเมื่อ:** 21 ก.ย. 2026 · **ยังไม่ได้ตัดสินใจเลือกแนวทาง**

ตอนนี้ระบบออกแบบมาสำหรับคนเดียว (Oat) ทุกอย่างวิ่งผ่าน `cfg` ตัวเดียวจาก `load_config()` และ `main.py` เรียกใช้ที่เดียว ทำให้ขยายเป็นหลายคนได้ไม่ยากในเชิงโค้ด แต่มีเรื่องความเป็นส่วนตัวและภาระดูแลที่ต้องตัดสินใจก่อน

## 3 แนวทาง

### A. แยก repo คนละอัน (template repo)

แต่ละคน fork repo แล้วตั้ง secrets ของตัวเอง ไม่ต้องแก้โค้ดเลย แค่ทำ README ให้ละเอียดและตั้ง repo เป็น template

| ข้อดี | ข้อเสีย |
|---|---|
| ข้อมูลสุขภาพและ token อยู่กับเจ้าตัว | คนใช้ต้องมีบัญชี GitHub และตั้ง secrets เป็น |
| ไม่ต้องรับผิดชอบข้อมูลของใคร | ถ้าโค้ดหลักแก้ ต้องให้แต่ละคน sync เอง |
| ค่า AI ต่างคนต่างจ่าย (~$0.30/เดือน) | ใช้กับคนที่ไม่สายเทคไม่ได้ |

### B. repo เดียว หลายคน (multi-tenant บน GitHub Actions) — แนะนำสำหรับกลุ่มเพื่อน 3–10 คน

repo เดียววนรันให้ทุกคน ใช้สแต็กเดิมทั้งหมด

| ข้อดี | ข้อเสีย |
|---|---|
| คนใช้แค่ส่ง token กับ webhook ไม่ต้องมี GitHub | **token และข้อมูลสุขภาพของทุกคนอยู่ในมือเจ้าของ repo** |
| แก้โค้ดครั้งเดียว ได้ผลกับทุกคน | ค่า AI รวมอยู่ที่เจ้าของ ($0.30 × จำนวนคน) |
| ใช้ cron และ workflow ชุดเดิม | ไฟล์ `.db` ของทุกคนถูก commit เข้า repo เดียวกัน |

### C. บริการเต็มรูปแบบ (Discord bot + server + ฐานข้อมูล)

ผู้ใช้เชื่อม Garmin เองผ่าน bot มีระบบสมัคร ลบข้อมูล และเข้ารหัส token

- ขยายได้ไม่จำกัด คนใช้ง่ายที่สุด ไม่ต้องพึ่งเจ้าของ repo
- ต้องมี server ที่รันตลอดเวลา ฐานข้อมูลจริง (เช่น Postgres) ระบบเข้ารหัส token และงานดูแลต่อเนื่อง
- เกินขอบเขตของสแต็กปัจจุบัน (GitHub Actions ไม่พอ) และต้องทบทวนเงื่อนไขการใช้งานของ Garmin อย่างจริงจัง

## แบบละเอียดของแนวทาง B

### การตั้งค่า

Variable `USERS` เก็บ JSON ของทุกคน ส่วนของลับแยกเป็น secret ต่อคน

```json
[
  {
    "id": "oat",
    "tz": "Asia/Bangkok",
    "send_deadline": "06:45",
    "races": [
      {"name": "KKIM 2027", "type": "road", "date": "2027-01-10", "priority": "A"}
    ]
  },
  {"id": "ploy", "tz": "Asia/Bangkok", "send_deadline": "05:30", "races": []}
]
```

| ของลับต่อคน | ชื่อ secret |
|---|---|
| Garmin token | `GARMINTOKENS_BASE64_<ID ตัวพิมพ์ใหญ่>` |
| Discord webhook | `DISCORD_WEBHOOK_<ID ตัวพิมพ์ใหญ่>` |

API key ของ LLM ใช้ร่วมกันตัวเดียว (`ANTHROPIC_API_KEY`) เหมือนเดิม

### ข้อมูล

- แยกฐานข้อมูลคนละไฟล์: `data/oat.db`, `data/ploy.db` ลบของใครก็ลบไฟล์เดียว ไม่กระทบคนอื่น
- ตาราง `notifications` แยกตามไฟล์อยู่แล้ว จึงไม่ต้องเพิ่มคอลัมน์ user

### การรัน

- `python main.py --user oat` รันเฉพาะคนนั้น
- ถ้าไม่ระบุ `--user` ให้วนทุกคนตามลำดับ ครอบ try/except ต่อคน คนหนึ่งพังไม่กระทบคนอื่น
- ข้อความเตือน token หมดอายุส่งไปที่ webhook ของเจ้าตัวเอง ไม่ใช่ของเจ้าของ repo
- exit code: 0 ถ้าอย่างน้อยหนึ่งคนสำเร็จ, 1 ถ้าพังหมด (ให้ workflow ยังไม่ fail เวลาคนเดียวมีปัญหา)

### Workflow

- ใช้ cron ชุดเดิม (`0,30 22-23 * * *` และ `45 23 * * *`)
- **รันเป็น job เดียววนทุกคน ไม่ใช้ matrix** เพราะหลาย job จะแย่งกัน commit ไฟล์ `.db` จน push ชนกัน
- `SEND_DEADLINE` แยกต่อคนได้ เพราะแต่ละคนออกวิ่งคนละเวลา ช่วง cron ต้องครอบเวลาของคนที่ออกวิ่งเช้าที่สุด
- ระวังเพดาน request ของ Garmin: ปัจจุบันจำกัด ~250 request ต่อรอบ ถ้ามีหลายคนต้องนับรวมทุกคน (แต่ละคนใช้ ~36 request ต่อรอบเมื่อ `REFRESH_DAYS=7`)

### สิ่งที่ต้องแก้ในโค้ด (ประมาณ 150 บรรทัด)

| ไฟล์ | สิ่งที่ต้องทำ |
|---|---|
| `config.py` | เพิ่ม `load_users()` คืน list ของ `Config` อ่านจาก `USERS` + secret ตาม id, validate ทีละคน คนที่ตั้งค่าผิดให้ log warning แล้วข้าม ถ้าไม่มี `USERS` ให้ถอยไปใช้ค่าเดิมแบบคนเดียว (backward compatible) |
| `main.py` | แยก `run_for_user(cfg, args) -> int` ออกจาก `main()` แล้ววนเรียก เพิ่ม `--user <id>` |
| `storage.py` | ไม่ต้องแก้ แค่ส่ง path ต่างกัน |
| `analysis.py`, `summarize.py`, `discord_notify.py` | ไม่ต้องแก้ ทั้งหมดรับ config/ผลลัพธ์เข้ามาอยู่แล้ว |
| `setup_tokens.py` | เพิ่ม `--user <id>` แล้วพิมพ์คำสั่ง `gh secret set GARMINTOKENS_BASE64_<ID> < ไฟล์` ให้เจ้าตัวรันเอง จะได้ไม่ต้องส่ง token ผ่านแชตหรืออีเมล |
| `tests/` | เพิ่มเคสหลายผู้ใช้, เคสที่ผู้ใช้คนหนึ่งพังแล้วคนอื่นยังส่งได้, เคส `USERS` ที่ JSON ผิด |
| `CLAUDE.md` | อัปเดตหัวข้อ 4 (config), 7 (storage), 11 (orchestrator), 12 (workflow) **ก่อน** เขียนโค้ด |

## ความเสี่ยงที่ต้องจัดการก่อนเปิดให้คนอื่นใช้

1. **token Garmin เท่ากับกุญแจบัญชี** ใครถือ token เข้าถึงข้อมูล Garmin ทั้งหมดของคนนั้นได้ ถ้าเลือก B เจ้าของ repo ต้องรับผิดชอบเรื่องนี้เต็ม ๆ
2. **ข้อมูลสุขภาพเป็นข้อมูลอ่อนไหวตาม PDPA** ถ้าเก็บของคนอื่นควรมีการขอความยินยอม บอกให้ชัดว่าเก็บอะไร เก็บที่ไหน เก็บนานแค่ไหน และลบให้ได้เมื่อเจ้าตัวขอ
3. **`garminconnect` เป็น API ไม่เป็นทางการ** ใช้ส่วนตัวความเสี่ยงต่ำ แต่การให้บริการคนอื่นมีโอกาสผิดเงื่อนไขการใช้งานของ Garmin
4. **repo ต้องเป็น private เสมอ** ยิ่งมีข้อมูลหลายคนยิ่งสำคัญ (กฎข้อนี้มีอยู่แล้วใน CLAUDE.md หัวข้อ 2)
5. **ค่า AI** ถ้าเลือก B เจ้าของจ่ายคนเดียว ควรกำหนดเพดานหรือให้แต่ละคนใช้ key ของตัวเองก็ได้ (เพิ่ม `anthropic_api_key` ต่อคนใน `USERS` ได้)
